het probleem

"Even snel live zetten" is nooit even snel.

Eén collega weet hoe de uitrol werkt. De testomgeving loopt drie versies achter. En elke release is een middag klikken, kopiëren en duimen. Dus stellen jullie releases uit, en groeit elke release in omvang én risico.

DevOps draait die spiraal om. Elke wijziging wordt automatisch gebouwd en getest vóór hij gemerged mag worden. Elke release volgt exact dezelfde, controleerbare route naar staging en productie. Kleinere stappen, minder risico, sneller resultaat. En niemand meer die 's avonds handmatig bestanden staat te kopiëren.

de aanpak

Eerst één project goed.

Plannen

We kiezen samen het project dat als eerste door de pipeline gaat: groot genoeg om ervan te leren, klein genoeg om snel live te zijn.

Inrichten

Azure DevOps opgezet zoals het hoort: private repositories, branch-beleid, boards voor features en prioriteiten, rechten die kloppen.

Automatiseren

Build- en testpipeline bij elke pull request; pas als alle tests slagen kan er gemerged worden. Daarna automatische uitrol naar de omgevingen die jullie kiezen.

Overdragen

We leggen jullie team uit hoe build en uitrol geconfigureerd zijn, zodat elk volgend project hetzelfde patroon volgt, zonder ons.

veelgestelde vragen

Eerst nog even dit.

We hebben nog geen geautomatiseerde tests. Heeft een pipeline dan zin?

Ja. De pipeline dwingt structuur af vanaf dag één; tests groeien daarna mee. Elke nieuwe test die erbij komt, draait voortaan automatisch bij elke wijziging.

Werkt dit ook als we niet naar Azure uitrollen?

Ja. Azure DevOps kan ook uitrollen naar on-premise servers of andere omgevingen. De pipeline-structuur blijft hetzelfde.

Moet ons team Azure DevOps al kennen?

Nee. De overdracht hoort bij het traject: we leggen uit hoe build en uitrol geconfigureerd zijn, zodat het team zelf verder kan.

Welk project kiezen we als eerste?

Samen kiezen we een project dat groot genoeg is om van te leren en klein genoeg om snel live te zijn. Daarna volgt de rest hetzelfde patroon.
